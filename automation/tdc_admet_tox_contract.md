# TDC-ADMET-Tox Runtime Contract

## Topic

- Topic id: `tdc_admet_tox`
- Topic label: `TDC-ADMET-Tox`
- Endpoints: `AMES`, `hERG`, `DILI`
- Public dataset root: `data/tdc_admet_tox/public`
- Public dataset env: `TDC_ADMET_TOX_DATASET_ROOT`
- Host-only label env: `TDC_ADMET_TOX_HIDDEN_LABELS_ROOT`
- Contract file: `automation/tdc_admet_tox_contract.md`

## Objective

Evaluate whether a research framework can form reasonable molecular-ML hypotheses, run a fixed number of reproducible experiments, select a result from validation evidence, and write a short evidence-backed paper. The task is offline, lightweight, reproducible, and auditable.

## Visible Inputs

The framework may receive only:

- `train.csv` and `validation.csv`, including labels
- `test.csv`, without labels
- `docs/tdc_admet_tox_feature_generation_contract.md`
- `docs/tdc_admet_tox_submission_spec.md`
- the scorer interface and output schema, but not scorer secrets or test labels
- this contract and the experiment requirements
- the fixed compute budget in `docs/tdc_admet_tox_compute_budget.md`

The public data is projected from host-trusted normalized endpoint exports with `automation/scripts/materialize_tdc_admet_tox_dataset.py`. Source exports and their caches remain host-only and are not framework inputs.

The framework must not receive the host-only test-label root, a score derived from hidden test labels, or artifacts from another framework's run.

## Primary Metric

The main leaderboard score is the unweighted arithmetic mean of the three endpoint AUROCs:

```text
Main Score = (AUROC_AMES + AUROC_hERG + AUROC_DILI) / 3
```

Only this value determines the main ranking. AUPRC, calibration, runtime, and reproducibility are secondary diagnostics and must not be folded into the main score.

## Required Outputs

Framework-produced outputs, written inside the current fresh run workspace:

- root-level `predictions.csv`
- root-level `research_idea.json`, written and locked before the first validation experiment
- root-level `experiment_trace.json`
- runnable code and a recorded reproduction command
- complete per-experiment logs and configuration files
- `paper.md`, or `paper.pdf` plus a machine-auditable Markdown claim sidecar
- framework-authored `final_report.md`
- root-level `environment.json`

Host-produced output, created only after the framework has exited:

- root-level `score.json`, generated by `automation/scripts/run_tdc_admet_tox_host_score.py`

The framework must not create, estimate, backfill, or modify `score.json`. A valid evaluation runs the artifact validator once at the `framework` stage, invokes the host scorer, and then runs the validator at the `final` stage.

## Test-Label Isolation

- Public inputs and hidden labels must live under separate physical roots.
- `TDC_ADMET_TOX_DATASET_ROOT` must resolve to the public root only.
- `TDC_ADMET_TOX_HIDDEN_LABELS_ROOT` is available only to the host scorer and must never be mounted into a framework container.
- The repository root must not be mounted as a writable framework workspace.
- The host scorer must reject a hidden-label file located under the public dataset root.
- `predictions.csv` contains probabilities only and must not contain a label column.

## Experiment Budget

- Run at least 2 and at most 4 complete experimental configurations.
- A configuration is a distinct model, training, or feature strategy evaluated on validation data.
- A configuration contains exactly one validation-evaluated candidate. An internal sweep counts once per candidate, not once per launcher command.
- Every experiment must have a hypothesis, immutable config, validation predictions, validation metrics, and a log.
- At least two complete configurations must have distinct config content and distinct declared strategies.
- Experiments 3 and 4 are permitted only as specific follow-ups to evidence from the current best validation run.
- Never begin a fifth configuration. Stop exploration immediately after the final permitted experiment and select using validation evidence only.
- Use at most 4 vCPU, 16 GiB memory, 10 GiB writable disk, 3,600 seconds cumulative experiment runtime, and 7,200 seconds total framework wall time. GPU use is prohibited.

## Claim Traceability

Every empirical number in a paper table, and every quantitative empirical claim in prose, must reference a unique `claim_id` from `experiment_trace.json`. A claim record must contain:

```json
{
  "claim_id": "table1_ames_auroc_model_b",
  "endpoint": "AMES",
  "metric": "AUROC",
  "value": 0.8421,
  "source_run_id": "run_003",
  "prediction_file": "runs/run_003/predictions_ames.csv",
  "config_file": "runs/run_003/config.json",
  "log_file": "runs/run_003/train.log"
}
```

Markdown references use `<!-- claim:table1_ames_auroc_model_b -->` in the same table cell or immediately after the quantitative prose claim. Claim values must match the referenced validation metrics artifact. Hidden-test results must not appear in the framework-authored paper because they do not exist until host scoring.

## Audit And Reproduction

- Follow `docs/tdc_admet_tox_experiment_requirements.md` and `automation/tdc_admet_tox_execution_budget.md`. The framework owns the order and rationale of its experiments; the host does not prescribe a baseline, method sequence, or promotion workflow.
- Validate framework artifacts with `automation/scripts/validate_tdc_admet_tox_run.py --stage framework --public-dataset-root /data/tdc_admet_tox` before scoring.
- Generate the official result with `automation/scripts/run_tdc_admet_tox_host_score.py` on the host.
- Validate the completed package with `automation/scripts/validate_tdc_admet_tox_run.py --stage final`.
- Record source-data revisions and file hashes when the dataset is materialized.
- Ensure framework images and writable homes do not contain PyTDC/TDC data caches with test labels.
- Run offline after materialization: no runtime downloads, web queries, remote feature lookup, or test-label access.

## Scope Guard

- Do not route this topic to GAVE2, ARC-WBE-2026, PsyDefDetect, BabyLM, or their datasets, wrappers, scorers, contracts, and workspaces.
- Fixed framework workspaces are template sources only.
- Every evaluation uses a fresh physical workspace under `real_eval/runs/<run_id>/<framework_slug>/workspace`.
- Framework outputs may be written only under the current `REAL_EVAL_RUN_ROOT`.
