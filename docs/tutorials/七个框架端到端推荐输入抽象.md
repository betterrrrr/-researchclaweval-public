# 七个框架端到端推荐输入抽象

## 1. 目的

这份文档不复述当前仓库里已经验证过的 `docker run` 命令，而是把 7 个项目做端到端实验时真正需要的“初始输入”抽象出来，便于后续换题、换数据、换实验目标时直接套用。

这里的“输入”指的是框架在启动一轮完整研究闭环前最需要的人类提供信息，不是 API key、挂载路径或镜像参数。

## 2. 本文依据

- `tasks/01` 到 `tasks/07` 中的 `Minimal Input`、`Required E2E Flow`、`Verification Command`
- `Report/*_report.md` 中记录的最小 E2E 路径
- 各项目 `README`、模板文件、最小 E2E 脚本
- 轻量容器入口确认
  - `ai-researcher:runtime-ready` 中确认 `run_tiny_cls_local_e2e.py --help`
  - `ai-scientist-v2:runtime-ready` 中确认 `run_ideation.py --help`
  - `deepscientist:runtime-ready` 中确认 `ds --help`
  - `evoscientist:runtime-ready` 中确认 `evosci --help`

## 3. 先看结论

| 项目 | 原生输入接口 | 推荐输入载体 | 推荐抽象粒度 |
|---|---|---|---|
| AI-Researcher | idea description 或 reference-based ideation | 详细研究想法文本，或参考论文集合 | 中到高 |
| AI-Scientist-v2 | workshop topic file | 结构化 Markdown | 高 |
| ARIS | `/research-pipeline` 或 `RESEARCH_BRIEF.md` | 一句方向 + 最好附详细 brief | 高 |
| AutoResearchClaw | `researchclaw run --topic "..."` | 一句 topic | 中 |
| DeepScientist | `ds new "..."` / quest brief | 一句 research goal，后续落为 `brief.md` | 中 |
| dr-claw | `research_brief.json` | 结构化 JSON 研究简报 | 很高 |
| EvoScientist | `-p "..."` | 带任务约束和产物约束的长 prompt | 很高 |

一句话总结：

- 最“轻”的是 `AutoResearchClaw`、`DeepScientist`，一句 topic 就能开跑。
- 最“规范”的是 `AI-Scientist-v2`、`dr-claw`，它们明显偏结构化 brief。
- 最“提示工程化”的是 `EvoScientist`，它最适合直接给出可执行目标和产物约束。
- `ARIS` 介于 workflow 和文档驱动之间，最适合“详细 brief + workflow 命令”组合。

## 4. 推荐统一研究题材

如果只是想最小代价验证一个框架是否真的能跑完整条研究链，建议统一使用下面这类题材：

```text
基于 sklearn iris 或 digits 小数据集，提出并测试一个轻量改进想法，例如标准化、特征选择、或小规模超参数调整对简单分类器 baseline 的影响。要求生成研究计划，执行最小实验，产出结果图或表，分析结果，并写出简短论文式报告。
```

理由：

- 小数据，几乎无外部下载成本
- baseline 明确，容易收敛到“能执行”的实验
- 足够支持 idea、experiment、analysis、write-up 全链路
- 适合容器内快速复现

## 5. 各框架推荐输入抽象

### 5.1 AI-Researcher

原生接口特征：

- README 明确分两级输入
- `Detailed Idea Description`
- `Reference-Based Ideation`

它真正需要的不是一句话题，而是“研究想法或参考材料”。

推荐输入形态：

- 如果你已经知道想做什么：给一段详细 idea description
- 如果你还没有具体方法：给参考论文列表，让它先做 ideation

推荐抽象模板：

```text
Research Goal:
Improve a simple classifier on sklearn iris or digits with a lightweight method.

Known Baseline:
Plain LogisticRegression.

Candidate Improvement Space:
StandardScaler, feature selection, simple hyperparameter tuning.

Constraints:
Use only local lightweight datasets. Keep runtime short. Produce code, metrics, one figure/table, and a concise paper-style write-up.

Success Criterion:
Show whether the improved variant beats or matches the baseline and explain why.
```

更适合它的原因：

- 它本身就区分“已有想法”和“基于参考文献发想”
- 它会继续拆成 idea、plan、experiment、paper agent
- 只给一句很短的 topic，容易把上下文留给它自己猜

### 5.2 AI-Scientist-v2

原生接口特征：

- 明确要求 `--workshop-file`
- 主题文件要包含 `Title`、`Keywords`、`TL;DR`、`Abstract`

它真正需要的是“结构化 workshop topic markdown”，不是普通 prompt。

推荐输入形态：

- 一份短但结构完整的 topic markdown

推荐抽象模板：

```markdown
# Title
[一句明确题目]

# Keywords
[3-8 个关键词]

# TL;DR
[1-2 句说明要探索什么]

# Abstract
[1 段说明问题、方法空间、约束、预期产物]
```

推荐内容重点：

- 题目不要泛到“机器学习”这种层级
- 要把问题边界写清楚
- 要提前说清楚是“轻量、低成本、最小实验”

为什么：

- 这个框架先 ideation，再生成 ideas JSON，再进 BFTS
- workshop brief 越结构化，后续 idea 质量越稳定

### 5.3 ARIS / Auto-claude-code-research-in-sleep

原生接口特征：

- 可直接 `/research-pipeline "topic"`
- 也支持文档输入 `RESEARCH_BRIEF.md`
- 仓库自带 `RESEARCH_BRIEF_TEMPLATE.md`、`EXPERIMENT_PLAN_TEMPLATE.md`、`NARRATIVE_REPORT_TEMPLATE.md`

它真正吃的是“研究方向 + 约束丰富的研究简报”，而不是只吃一句话。

推荐输入形态：

- 最佳实践：先写 `RESEARCH_BRIEF.md`，再跑 `/research-pipeline`
- 只做轻量验证时：一句具体方向也能启动，但最好补上文档

推荐抽象模板：

```markdown
# Problem Statement
[当前方法哪里不够好]

## Background
- Field:
- Sub-area:
- Key papers:
- What I already tried:
- What failed:

## Constraints
- Compute:
- Timeline:
- Target venue:

## What I'm Looking For
- New direction / improve baseline / diagnostic study

## Domain Knowledge
[直觉、假设]

## Non-Goals
[明确不要做什么]

## Existing Results
[已有结果或负结果]
```

为什么：

- ARIS 的 workflow 明显是文档驱动的
- 后续会产出 `IDEA_REPORT.md`、`FINAL_PROPOSAL.md`、`EXPERIMENT_PLAN.md`、`AUTO_REVIEW.md`
- 如果最初输入不够结构化，后面的 experiment-bridge 和 paper-writing 容易漂

### 5.4 AutoResearchClaw

原生接口特征：

- 官方主入口就是 `researchclaw run --topic "Your research idea" --auto-approve`
- README 和内部文档都把“单个 research topic”作为起点

它真正需要的是一句明确研究 topic。

推荐输入形态：

- 一句 topic
- 但这句 topic 最好同时包含任务对象、改进空间和约束

推荐抽象模板：

```text
On sklearn iris or digits, investigate whether a lightweight improvement such as feature scaling, feature selection, or small hyperparameter tuning can improve a simple classifier baseline, and generate a concise paper-style report with figures and deliverables.
```

写法建议：

- 不要只写“improve classification”
- 最好同时包含 dataset、baseline 类型、候选改进空间、期望交付物

为什么：

- 这个框架就是围绕一个 topic 驱动 23-stage pipeline
- 它自己会做 literature、proposal、experiment、paper、review、deliverables
- 因此人类输入不必写成 JSON，但 topic 必须足够具体

### 5.5 DeepScientist

原生接口特征：

- `ds new "..."` 直接从一句 research goal 创建 quest
- quest 创建后会把输入落为 `brief.md`
- README 明确支持从 paper、repository 或 natural-language goal 启动

它真正需要的是一句可执行 research goal。

推荐输入形态：

- 一句自然语言目标
- 这句话应该同时定义任务和最小实验边界

推荐抽象模板：

```text
On sklearn iris, run a minimal classifier-improvement loop with one tiny experiment, compare a simple baseline against one stronger lightweight variant, analyze the result, and produce a concise report.
```

更适合它的原因：

- DeepScientist 的核心单位是 quest
- 它会把初始目标转成 `brief.md`、`plan.md`、`status.md`
- 一开始给过多细节不是必须，但目标必须足够“像一个可管理的 quest”

### 5.6 dr-claw

原生接口特征：

- 不是单纯一句 prompt
- 最小 E2E 脚本里直接构造了 `.pipeline/docs/research_brief.json`
- 其五阶段是 `Survey → Ideation → Experiment → Publication → Promotion`

它真正需要的是结构化 `research_brief.json`。

推荐输入形态：

- JSON research brief
- 至少覆盖 meta、survey、ideation、experiment、publication、promotion

推荐抽象模板：

```json
{
  "meta": {
    "title": "研究标题",
    "objective": "一句目标"
  },
  "sections": {
    "survey": {
      "literature_scope": "调研边界",
      "key_references": ["参考1", "参考2"],
      "synthesis_summary": "当前认识",
      "open_gaps": ["待验证缺口"]
    },
    "ideation": {
      "research_goal": "想验证什么",
      "problem_framing": "为什么值得做",
      "evidence_plan": "准备如何取证",
      "success_criteria": ["成功标准1", "成功标准2"]
    },
    "experiment": {
      "hypothesis_or_validation_goal": "实验假设",
      "dataset_or_data_source": "数据来源",
      "method_or_protocol": "方法和流程",
      "evaluation_plan": "指标和输出"
    },
    "publication": {
      "paper_outline": "写作提纲",
      "figures_tables_plan": "图表计划",
      "artifact_plan": "引用哪些产物"
    },
    "promotion": {
      "slide_outline": "分享提纲",
      "homepage_plan": "主页摘要"
    }
  }
}
```

为什么：

- dr-claw 原生就会把项目管理成多阶段研究工作区
- 它不仅要实验，还要 publication 和 promotion
- 如果没有结构化 brief，它很难稳定地产生五阶段原生产物

### 5.7 EvoScientist

原生接口特征：

- CLI 主入口支持 `-p "..."` 单次执行
- 但验证脚本实际使用的是“长 prompt + 明确产物路径要求”
- 框架自身流程是 `intake → plan → execute → evaluate → write → verify`

它真正需要的不是简短题目，而是“任务要求 + 执行约束 + 产物约束”。

推荐输入形态：

- 一段长 prompt
- 明确告诉它要生成什么文件、跑什么实验、输出到哪里

推荐抽象模板：

```text
Create a minimal reproducible experiment on sklearn iris or digits.
Use one simple baseline and one lightweight improved variant.
Actually execute the experiment.
Write numeric results to /artifacts/results/results.md.
Save one chart to /artifacts/results/accuracy.png.
Write a concise final report to /final_report.md.
Keep runtime short and do not install extra dependencies.
Ensure all output files exist at the end.
```

为什么：

- EvoScientist 是 agentic CLI，不是固定论文模板引擎
- 它对“你到底想落哪些文件”很敏感
- 给清楚产物 contract，通常比只给 topic 更稳

## 6. 推荐输入强度排序

如果按“需要用户一开始提供多少结构化信息”排序，从低到高大致是：

1. AutoResearchClaw
2. DeepScientist
3. AI-Researcher
4. ARIS
5. AI-Scientist-v2
6. EvoScientist
7. dr-claw

解释：

- `AutoResearchClaw`、`DeepScientist` 最能从一句目标自己展开
- `AI-Researcher` 能展开，但更依赖你先给 idea 或 references
- `ARIS` 和 `AI-Scientist-v2` 明显受益于结构化文档
- `EvoScientist`、`dr-claw` 最适合“输入即契约”

## 7. 推荐统一输入改写规则

如果以后要把任意新课题迁移到这 7 个框架，建议先把课题改写成下面这 6 个槽位，再映射到具体框架：

1. `Problem`
   当前问题是什么，为什么值得研究。
2. `Scope`
   数据集、任务、方法边界是什么。
3. `Baseline`
   至少有一个可比较 baseline。
4. `Improvement Space`
   允许 AI 探索哪些轻量改动。
5. `Success Criteria`
   什么结果算成功，至少需要哪些图表或指标。
6. `Deliverables`
   最终要生成哪些代码、分析、图表、报告文件。

映射方式：

- AI-Researcher：偏 `Problem + Baseline + Improvement Space`
- AI-Scientist-v2：偏 `Problem + Scope + Deliverables`
- ARIS：六项都建议给
- AutoResearchClaw：至少给前五项，压缩成一句 topic
- DeepScientist：至少给 `Problem + Scope + Deliverables`
- dr-claw：六项都适合写进 JSON brief
- EvoScientist：六项都适合直接写进 prompt

## 8. 最终建议

如果目标是“最低成本验证框架能否完成完整科研闭环”，推荐这样选输入方式：

- `AI-Researcher`：详细 idea description
- `AI-Scientist-v2`：四段式 workshop markdown
- `ARIS`：`RESEARCH_BRIEF.md` + `/research-pipeline`
- `AutoResearchClaw`：一句具体 topic
- `DeepScientist`：一句可执行 research goal
- `dr-claw`：结构化 `research_brief.json`
- `EvoScientist`：带产物路径要求的长 prompt

不要统一把 7 个框架都喂成同一种“短 prompt”。它们虽然都能做端到端科研，但输入契约并不一样。
