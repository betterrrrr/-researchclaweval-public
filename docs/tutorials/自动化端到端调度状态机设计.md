# 自动化端到端调度状态机设计

## 1. 目标

在 `$RESEARCHCLAWEVAL_ROOT` 中为现有 7 个 Agent 建立一套自动化运行框架，用于：

- 先执行 `smoke test`
- `smoke test` 通过后再执行最小端到端运行
- 基于 `systemd --user` 提交和托管真正的端到端阶段任务
- 基于本地 `codex exec` 的 headless 模式做调度、诊断、修复和推进
- 固定 Provider 使用方式
- 固定 Semantic Scholar API 使用方式
- 按顺序推进 ToDoList

这套系统的关键要求是：

- `smoke test` 在 headless `codex exec` 中同步阻塞执行
- 只有真正的 `e2e` 通过 `systemd --user` 非阻塞提交
- `codex exec` 不长期挂起等待 `e2e` 任务结束
- 初始 headless `codex exec` 必须在同一会话里完成 `smoke -> 成功后 dispatch e2e -> 退出`
- follow-up headless `codex exec` 必须使用全新的上下文，读取刚结束的 `systemd --user` 结果，再决定推进下一个项目还是修复当前项目
- 所有 headless `codex exec` 都必须使用 `--yolo`
- 模型固定为 `gpt-5.4`
- 推理强度固定为 `medium`
- 当前运行 topic 必须通过一个可替换的 topic contract 文件注入，smoke 阶段先检查并修正真实 e2e 输入，再决定是否允许 dispatch

## 2. 核心结论

### 2.1 本地执行器

自动化系统使用本机本地 `codex exec`，不是远端调度器：

- Codex binary: `$REAL_EVAL_HOST_NODE_ROOT/bin/codex`
- Wrapper: `$RESEARCHCLAWEVAL_ROOT/codex_runs/bin/codex-wrapper`

建议统一通过 wrapper 调用，避免不同脚本中混用多个 `codex` 路径。

### 2.2 职责分层

系统分为三层：

1. `systemd --user`
   - 只负责提交并运行真正的 `e2e` 阶段任务
   - 负责托管长期运行的端到端任务

2. 本地 `codex exec` headless
   - 负责执行同步阻塞的 `smoke test`
   - 负责读取状态
   - 负责读取日志
   - 负责决定“重跑 / 续跑 / 修复 / 推进下一个”
   - 负责在需要时发出下一条 `systemd-run --user ...`
   - 对 `smoke` 而言阻塞到命令结束
   - 对 `e2e` 调度而言发出命令后立即退出

3. Docker 镜像 / 容器
   - 负责真正执行各项目的 `smoke` 和 `e2e`

### 2.3 最重要的执行原则

`codex exec` 分两种工作模式：

- 初始模式：在同一个 headless 会话中同步阻塞执行 `smoke`，若通过则继续在同一会话中提交 `e2e`
- follow-up 模式：在全新的 headless 会话中读取已结束的 `systemd --user` 结果，做成功推进或失败修复/重提

也就是说：

1. headless `codex exec` 启动
2. 先同步执行当前项目的 `smoke`
3. 若 `smoke` 失败，则在本轮内直接进入修复/重试决策；若仍失败则结束本轮并写失败状态
4. 若 `smoke` 通过，则在同一个 headless 会话中发出一条 `systemd --user` 的 `e2e` 任务
5. 提交成功后，这次 headless `codex exec` 退出
6. systemd unit 独立运行 `e2e`
7. unit 结束后产生日志和状态文件
8. 下一次 headless `codex exec` 被自动唤醒，且这是全新的上下文
9. 它先查看刚结束的 unit 日志和状态
10. 若 `e2e` 成功，则推进 `todo` 下一个项目
11. 若 `e2e` 失败，则进入修复；修复成功后在同一个 follow-up 会话里重新提交一条新的 `systemd --user` 任务
12. 提交或阻断后，该 follow-up headless 会话退出

## 4. 活动图语义

本系统更接近 UML 的 **活动图（Activity Diagram）**。

主要活动流如下：

1. `codex exec` 读取运行规则和状态
2. `codex exec` 同步阻塞执行 `smoke`
3. 若 `smoke` 失败，则本轮 `codex exec` 直接进入修复/重试决策
4. 若 `smoke` 通过，则本轮 `codex exec` 在同一会话里提交一个 `systemd --user` 的 `e2e` 任务
5. 提交成功后，本轮 `codex exec` 退出
6. `systemd` 独立运行 `e2e`
7. `systemd` 任务结束后，自动唤醒一个全新上下文的 headless `codex exec`
8. 若 `e2e` 通过，则这一轮新的 `codex exec` 推进下一个项目的 `smoke`
9. 若 `e2e` 失败，则这一轮新的 `codex exec` 决定：
   - 修复后 fresh rerun
   - 基于已有状态续跑
   - 返工当前项目
   - 标记阻塞

## 5. 状态机设计

### 5.1 状态集合

建议使用以下状态：

```text
PENDING_SMOKE
RUNNING_SMOKE
SMOKE_PASSED
SMOKE_FAILED

PENDING_E2E
RUNNING_E2E
E2E_PASSED
E2E_FAILED

CODEX_REPAIRING
RETRY_SMOKE
RERUN_E2E_FRESH
RESUME_E2E
ADVANCE_NEXT
BLOCKED
COMPLETED
```

### 5.2 状态转移

```text
PENDING_SMOKE -> RUNNING_SMOKE -> SMOKE_PASSED -> PENDING_E2E
PENDING_SMOKE -> RUNNING_SMOKE -> SMOKE_FAILED -> CODEX_REPAIRING

PENDING_E2E -> RUNNING_E2E -> E2E_PASSED -> ADVANCE_NEXT
PENDING_E2E -> RUNNING_E2E -> E2E_FAILED -> CODEX_REPAIRING

CODEX_REPAIRING -> RETRY_SMOKE -> RUNNING_SMOKE
CODEX_REPAIRING -> RERUN_E2E_FRESH -> RUNNING_E2E
CODEX_REPAIRING -> RESUME_E2E -> RUNNING_E2E
CODEX_REPAIRING -> ADVANCE_NEXT -> next project PENDING_SMOKE
CODEX_REPAIRING -> BLOCKED
```

### 5.3 “基于已经成型的跑”

这个动作不要和“fresh rerun”混用，建议明确为：

- `RESUME_E2E`

含义：

- 当前项目已有部分中间产物或运行状态
- 无需从空目录重启整个 E2E
- 基于当前有效状态继续推进

## 6. systemd user 提交模型

### 6.1 统一模式

不建议让每个项目自己管理 service 文件。

建议统一由 orchestrator 只为 `e2e` 提交 transient unit：

```bash
systemd-run --user --unit researchclaweval-05-e2e-attempt-003 ...
```

### 6.2 优点

- unit name 自带项目编号和 `e2e` 阶段信息
- 日志天然进入 journald
- 每次 attempt 都能独立追踪
- 便于 headless `codex exec` 基于日志做决策

### 6.3 基本规则

每次 `codex exec` 的规则应拆开看：

- `smoke`：在 `codex exec` 中同步阻塞执行，执行完才进入下一步
- `e2e`：由 `codex exec` 发出一条 `systemd-run --user` 命令
- 对 `e2e` 而言，不持续轮询，不等待 unit 结束，发出后立即退出

## 7. 真实状态来源

下一轮决策不应依赖自然语言对话，而应依赖以下确定性状态源：

1. `systemctl --user status <unit>`
2. `journalctl --user -u <unit>`
3. 运行状态 JSON
4. 退出码文件
5. 产物检查 JSON
6. 项目实际产物目录

换句话说，真正的“系统真相”是：

- exit code
- artifact existence
- state file
- journald logs

而不是 `last_message.txt` 的自然语言。

## 8. Codex Exec 的职责边界

### 8.1 允许做的事

headless `codex exec` 负责：

- 读取 `AGENTS.md`
- 读取运行 ToDoList
- 读取项目状态文件
- 同步阻塞执行当前项目的 `smoke`
- 读取最新 unit 日志
- 定位错误
- 修改脚本 / 配置 / 源码中的最小必要修复
- 决定下一步是 retry、resume、rerun 还是 advance
- 在 `smoke` 通过后发出下一条 `systemd-run --user` 的 `e2e` 命令

### 8.2 不负责的事

headless `codex exec` 不负责：

- 持续守候 `e2e` unit 完成
- 直接作为长期 daemon
- 用自然语言作为唯一控制面

### 8.3 必须输出结构化决策

每次 headless `codex exec` 结束前，必须写一个结构化决策文件，而不是只写一句自然语言。

建议格式：

```json
{
  "project": "05_DeepScientist",
  "phase": "e2e",
  "status": "failed",
  "decision": "resume_e2e",
  "reason": "workspace artifacts already exist; continue from current quest state",
  "patched_files": [
    "codex_runs/deepscientist_e2e_in_container.sh"
  ],
  "next_unit": "researchclaweval-05-e2e-attempt-004",
  "next_cmd": "automation/scripts/run_e2e.sh 05_DeepScientist --resume"
}
```

orchestrator 只读取这个结构化文件，不依赖自然语言描述。

## 12. smoke / e2e 执行原则

### 12.1 smoke

`smoke` 的作用是快速验证：

- 镜像可拉起
- 必要挂载和 env 配置正确
- 入口命令可执行
- 必要依赖可见
- 必要 API 配置已生效
- 执行位置固定在当前这轮 headless `codex exec` 内，同步阻塞完成

### 12.2 e2e

`e2e` 的作用是：

- 基于已通过的 `smoke`
- 执行项目级最小端到端运行
- 使用已存在并确认过的最小命令
- 验证最小核心产物已经生成
- 执行方式固定为 `systemd --user` 非阻塞提交

### 12.3 命令来源

优先使用 `Report/*_report.md` 中已经记录好的最小 E2E 命令，不重新造入口。

若需要修正命令，应：

- 优先修配置和脚本
- 最后才改外层运行命令
- 改动后同步更新运行配置来源

## 13. 推荐的最小状态文件

每个阶段任务结束后，至少要写出一份最小状态记录。

`smoke` 示例：

```json
{
  "project": "05_DeepScientist",
  "phase": "smoke",
  "executor": "codex_exec",
  "exit_code": 0,
  "artifact_check": "passed",
  "decision_hint": "submit_e2e"
}
```

`e2e` 示例：

```json
{
  "project": "05_DeepScientist",
  "phase": "e2e",
  "executor": "systemd_user",
  "unit": "researchclaweval-05-e2e-attempt-003.service",
  "exit_code": 0,
  "artifact_check": "passed",
  "decision_hint": "advance_next"
}
```

这个最小状态记录比自然语言日志更重要，是下一轮调度的直接依据。

## 14. 一句话定稿

这套系统的标准运行语义应固定为：

> `systemd --user` 级别的命令由 `codex exec` 的 headless 模式发出；命令发出后，该次 headless `codex exec` 立即停止，不等待任务完成。任务完成后的状态判断由下一次被唤醒的 headless `codex exec` 基于 systemd 日志、退出码、状态文件和产物检查结果继续推进。

更精确的版本应为：

> `smoke test` 由当前这轮 headless `codex exec` 同步阻塞执行；只有真正的 `e2e` 才由 `codex exec` 通过 `systemd --user` 非阻塞提交。`e2e` 命令发出后，该次负责调度的 headless `codex exec` 立即停止，不等待任务完成。任务完成后的状态判断由下一次被唤醒的 headless `codex exec` 基于 systemd 日志、退出码、状态文件和产物检查结果继续推进。
